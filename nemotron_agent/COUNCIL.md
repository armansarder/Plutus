# Financial Decision Council — v2 local MVP

## Implemented behavior

The existing `/api/agent/run` contract stays at schema 1.0. Council uses separate
`/api/v2` routes and schema 2.0. Both feature flags default off. No branch merge,
push, public deployment, financial write, or Photon send is part of this change.

Four specialist chats use the same hosted Nemotron model with distinct system
prompts and isolated server-owned histories. Council performs a Leader framing call,
independent Budget/Risk reviews, a Simulator tool-selection/result/review exchange,
Budget/Risk evidence reviews, and a Leader synthesis. Maximum eight model calls;
up to two independent specialist calls concurrently; no automatic retries.
A direct Budget/Risk chat uses one model call; direct Simulator analysis uses two.
Educational replies use one call to select a bounded, vetted explanation. Purchase
analysis needs confirmed structured fields; message text never directly executes
amounts/dates. Debt/interest/investment comparisons return explicit unsupported
responses. Missing purchase inputs produce clarification rather than invented figures.

Models choose findings from the current verified catalog. Finding IDs, scenario
requests and positions are schema constrained and validated server-side. Financial
sentences, graph values and the final verdict are generated from deterministic
engine evidence, not unconstrained model arithmetic. This is a bounded financial
council, not a general financial chatbot or trained predictive model.

## Startup

From the updated repository root, use your existing Python environment or:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r nemotron_agent/requirements.txt
```

Keep your existing working Nessie configuration unchanged. The backend loads
`nemotron_agent/.env` automatically, with shell variables taking precedence. NVIDIA
and Nessie keys remain backend-only. In the shell that starts the backend:

```sh
export PLUTUS_COUNCIL_ENABLED=1
# FINPILOT_API_TOKEN must already contain your private service token (32+ characters).
python -m uvicorn nemotron_agent.main:app --host 127.0.0.1 --port 8003 --workers 1
```

For an intentional synthetic demo, set `AGENT_DATA_SOURCE=demo`,
`FINPILOT_DATA_SOURCE=mock`, and `FINPILOT_CUSTOMER_ID=synthetic_demo` in that shell.
Do not change the data mode as a fallback for Nessie failures. The demo snapshot
moves its fixed schedule relative to the current UTC date; omit explicit dates
when testing today's fixture. Live Nessie intraday snapshots start the next day.

In a second terminal from `frontend/`:

```sh
export VITE_DATA_MODE=remote
export VITE_COUNCIL_ENABLED=true
export FINPILOT_BACKEND_URL=http://127.0.0.1:8003
# Set FINPILOT_API_TOKEN privately to exactly the same value as the backend.
npm run dev -- --host 127.0.0.1 --port 8080
```

Alternatively copy `frontend/.env.example` to `frontend/.env.local`, fill the private
service token, then explicitly load server settings:

```sh
node --env-file=.env.local node_modules/vite/bin/vite.js --host 127.0.0.1 --port 8080
```

Open `http://localhost:8080/talk`. Choose Council, Budget, Risk or Simulator. A
conceptual question needs no purchase fields. For a financial comparison, check
"Include a confirmed purchase comparison" and confirm amount/date/reserve/horizon.
The UI shares the message and approved evidence only when model use is enabled.
Select "Share these findings with Council" for an explicit handoff. It shares
validated findings from that response, not the entire specialist conversation.
The original purchase-analysis interface remains one button away.

## Rollback / disable

Set `PLUTUS_COUNCIL_ENABLED=0` and restart the backend; v2 status reports disabled
and conversation routes reject requests. Set `VITE_COUNCIL_ENABLED=false` and restart
Vite (or rebuild for production) to restore the original Talk interface. No v1
route or response-field migration is required. Feature flags never grant access.

## API

All routes require the existing backend service bearer token. Conversation routes
also require a signed browser session generated by the frontend server proxy;
browser-provided session/Authorization headers are never forwarded as identity.
Never call the backend directly from a browser with the service token.

- `GET /api/v2/council/status`: enabled state and honest scope.
- `POST /api/v2/conversations`: `{ "role": "council|budget|risk|simulator" }`.
- `GET /api/v2/conversations/{id}`: this session's bounded history.
- `DELETE /api/v2/conversations/{id}`: clear an inactive temporary conversation.
- `POST /api/v2/conversations/{id}/messages`: synchronous, bounded analysis.
- `POST /api/v2/conversations/{id}/messages/{request_key}/cancel`: request cancellation.

Example message (omit analysis for education/clarification):

```json
{
  "request_key": "unique-client-request-001",
  "message": "Can I afford this purchase if my income is late?",
  "allow_model": true,
  "analysis": {
    "purchase_amount": "400.00",
    "reserve": "200.00",
    "horizon_days": 30,
    "allow_model": true
  }
}
```

Optional `expected_snapshot_id` rejects stale decisions with 409. Optional `handoff`
is an owned `conversation_id:run_id` reference accepted only by Council, and only
against the same financial snapshot. A new analysis always freezes a new snapshot;
it does not reuse another chat's mutable account state. Old chat findings are sent
as context only when their snapshot matches the current run.

The response includes role reviews, evidence references, revisions, actual observed
action events, a Passport-bearing v1 deterministic calculation object, and a typed
chart with aligned daily series, baseline differences, reserve headroom, minimums
and first reserve-breach markers. The inner analysis is explicitly deterministic;
outer council mode indicates whether model reviews completed. Its model_data_shared
field describes that calculation path, not the council's separate model calls.

No invented progress is streamed. Loading states describe pending work; completed
logs are shown after the synchronous response. IDs reference retained results only
inside temporary conversation history; there is no public run URL or background job.

## Safety, ownership and limits

A signed, opaque HttpOnly/SameSite=Strict cookie binds each browser to separate
backend conversations. The signing key is derived with a purpose prefix from the
server-only service token. Secure cookies are used on HTTPS. The backend validates
the signature and binds ownership to configured customer plus browser session.
Cross-session reads, writes, clear, handoffs and cancellation are rejected. Session
cookies hold no financial records. Financial history stays off browser storage/URLs.

This is isolation for one configured-customer local demo, **not a login system**.
Production mode rejects council activation until an authenticated application-user
mapping is integrated. V1 keeps its existing security/deployment behavior. Keep the
frontend local or behind an existing authenticated boundary; origin checks alone
are not access control. Do not publish this council demo as multi-user banking.

Storage is in-memory, single-worker, with 30-minute idle expiry, at most 32 total
conversations, eight conversations per session and eight submitted requests per
conversation. One active request per conversation, two active analyses per process.
Identical request keys return cached results; changed payloads with the same key
return 409. A new key is a new analysis and can incur model calls. Clear/new chat is
explicit. No persistence or encryption-at-rest claim is made.

The source fetch is bounded to 12 seconds and the council uses the remaining part
of a 60-second deadline. Each provider request has a 10-second network timeout;
outer deadline cancels pending HTTP calls and prevents further dispatch. Explicit
cancel/disconnect stops the asynchronous model workflow; a previously dispatched
provider request may already have been billed. Source reads execute in a bounded
thread call and may finish after timeout; they are read-only and trigger no model
calls after source failure. At most 200 upcoming events and 90 forecast days are
supported by this council MVP. Forecasts remain deterministic and conditional.

No account identifiers, raw merchant text, source notes or raw history enter model
context. User messages can contain personal information: UI warns against it, common
key/token patterns are redacted, and no payload logging is added. Other text is
untrusted context, never tool permission. Graph specs contain data, never generated
HTML/JS/code. Models cannot select arbitrary tool names or financial actions.

## Verification and limitations

```sh
python -m pytest tests -q
cd frontend
npm test
npx tsc --noEmit
VITE_DATA_MODE=remote VITE_COUNCIL_ENABLED=true npm run build
```

Synthetic fixtures and fake providers test the full role order, independent contexts,
evidence revisions, handoffs, idempotency, ownership, injection exclusion, unsupported
calculations, disabled/partial output, chart consistency and call deadlines. Existing
Nessie route tests remain in place. Live Nemotron verification must use synthetic
financial data first. Live Nessie checking requires the team's private configuration;
do not invent keys or silently switch data sources.

Deferred: arbitrary free-text amount extraction, trained forecasts/uncertainty bands,
debt amortization, goal dates, persistent chats, production user login, streaming,
voice/reminders and Photon delivery. Sensitivity or stochastic models need separately
validated modules. No guarantees about affordability or statistical success are made.

## Plain-language agent answers

Calculated reviews now include `recommendation` (a direct choice) and a short
`summary` reason derived from verified engine results. Budget addresses scheduled
cash flow, Risk addresses tested setbacks, Simulator suggests a tested date, and
Leader gives the final choice. The model selects only evidence-supported actions;
`conditional` and `insufficient_evidence` are not accepted for a completed purchase
recommendation when calculations support a clear choice. Educational answers and
failed/disabled model reviews do not invent a personalized recommendation.

The main view shows only the latest review per role. Earlier stages, raw evidence
references and charts are expandable. A suggested ordinary safe date is explicitly
conditional on the expected income schedule, never claimed to be stress-safe.
After updating: restart the backend, refresh the frontend, and submit a new analysis.
Previously returned results remain historical and are not rewritten.
